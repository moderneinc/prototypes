# #8530 — Common actions & discoverability: grounding + design approach

## 1. Grounded action inventory (from the real Builder code)

Actions the Builder actually has today (current `components/builder/*` + the #8500 reshuffle). We design against these — nothing invented.

**Global / Builder-level** (start or switch a whole custom recipe)
- New recipe · Open existing / Open recent · Import from YAML · Manage recipes · Import from V1
- (#8500 consolidates these into one "Builder recipe actions" modal opened from the `Builder ⌄` title.)

**Recipe-level** (the current recipe)
- Edit details · Edit as YAML · **Download YAML** (writes a `.yml` file — handler is `handleExportAsYaml`) · **Copy as YAML to clipboard** (`handleCopyYaml`) · Undo (⌘Z) · Dry run · Rename (inline) · Save (auto, with indicator)

**Node-level** (a recipe inside the tree — the row kebab)
- Add recipe to node · Edit options · Duplicate · Remove · Run this recipe only · View full details · Set as precondition

**Key finding — "Export" == "Download".** The file action is named `handleExportAsYaml` internally but surfaced as "Download YAML." Historically both verbs appeared, which is the confusion the research flagged. So #8530's five actions map to real functionality as:
- **Add** → Add recipe (node) / New / Open (global)
- **Edit** → Edit details / Edit options / Edit as YAML
- **Export** → the file download (same outcome as Download; the legacy synonym to retire)
- **Download** → Download YAML → file on disk
- **Copy** → Copy YAML → clipboard

Design implication: don't ship both "Export" and "Download" as near-duplicate labels. One clear **Download YAML** (→ file) and **Copy YAML** (→ clipboard), each named by its *destination*.

## 2. Competitive analysis — how loved dev tools surface actions

- **GitHub (the closest analog to our exact problem).** File view: `Raw` · `Blame` · and an overflow with **"Copy raw file"** / **"Download raw file"** / **"Copy permalink"** — every action names its *destination/outcome* (clipboard vs disk vs URL) and pairs with a distinct icon. The `Code ▾` split button anchors a primary action with related outputs beneath. → **Name the outcome, pair with an icon, group related exports.**
- **VS Code.** Three layered surfaces: the **command palette** (⌘⇧P — everything findable by name), **context menus** (object actions), and a small **always-visible toolbar** of high-frequency icons (tooltipped). Menus show keyboard shortcuts inline. → **Layer discoverability: palette for all, toolbar for frequent, context menu for object; always show shortcuts.**
- **Linear.** Keyboard-first **⌘K command menu**, minimal chrome, actions contextual to the selection. → **A command menu is the ultimate discoverability backstop.**
- **Figma.** "Copy as PNG / SVG / link" are explicitly separated; the Export panel names format + scale. → **When there are multiple export outcomes, separate and label them, never one ambiguous "export."**
- **Postman / Insomnia.** The primary action (**Send**) is a big anchored button; Import/Export are distinct, clearly-labeled operations. → **Anchor the primary action; keep import/export separate and named.**
- **JetBrains, Raycast, Notion.** Action rows are **icon + label + shortcut** triples; destructive actions sit apart under a divider. → **Icon+label+shortcut; separate destructive.**

## 3. The defensible design approach for #8530

Three tiers of action surfacing (progressive disclosure), scope-separated, outcome-named:

**Tier 1 — Primary, anchored, always visible:** `Dry run` (filled, top-right of the recipe panel).

**Tier 2 — Frequent / most-missed, first-class (NOT in an overflow):**
- **Download YAML** (download icon → file) and **Copy YAML** (clipboard icon → clipboard) surfaced as a visible, adjacent pair — GitHub-file-actions style — or an `Export ▾` split button that lists both. This is the core #8530 move.
- A clear **Add recipe** entry point.

**Tier 3 — Everything else, in the `⋮` overflow + the Builder-actions modal:** Edit details, Edit as YAML, Duplicate, Remove, View details (overflow); New / Open / Import / Manage / From V1 (modal from the `Builder ⌄` title).

**Cross-cutting:**
- **Scope separation** — recipe-scoped actions live by the recipe (toolbar + ⋮); global actions live at the title. (Matches #8500, VS Code, GitHub.)
- **Name the destination, not a vague verb** — retire the Export/Download double-naming; distinct icons reinforce file vs clipboard.
- **Discoverability aids** — tooltips on every control, keyboard hints in menus (⌘Z already), optional command-palette backstop.
- **A11y** — Morpheus sizing, ≥24px hit targets (WCAG 2.5.8), visible focus, icon+label for anything important (icon-only only when secondary + tooltipped).

## 4. The key insight vs #8500 (why this is the actual #8530 work)

**#8500 puts Download YAML and Copy YAML inside the `⋮` overflow menu.** That's still "buried in one menu" — the exact thing #8530's goal says to fix ("sit somewhere obvious rather than buried in one menu"). So the on-scope #8530 design contribution, on top of the #8500 baseline, is: **un-bury Download / Copy (and Add) from the overflow into obvious, clearly-distinct, outcome-named controls.**

This is defensible to engineers because it (a) reuses #8500's structure (minimal net-new), (b) maps 1:1 to patterns they use daily (GitHub file actions, VS Code toolbar/palette), (c) resolves the exact reported pain (missed download; download-vs-export confusion we proved is a real code-level double-naming), and (d) is grounded entirely in existing functionality.

## 5. What this means for the prototype
`8530-builder-2-common-actions-discoverability.html` = replicate #8500 in Morpheus (baseline) **+** apply Tier 1/2/3: pull Download & Copy out of `⋮` into a visible, distinct pair (or `Export ▾` split), keep a clear Add entry, distinct icons/wording, Morpheus a11y sizing. Meets all three acceptance criteria.
