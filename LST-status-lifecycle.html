Moderne LST — service blueprint

How a Lossless Semantic Tree travels from a registered repository to a finished recipe run — mapped across the people, the platform surface, the worker engine, and the infrastructure behind them. Two long-lived phases (1–4, one per repo) feed two short-lived ones (5–7, fired on every run).

⚠ Gaps the cells can't show

Per-status problems are already flagged with ⚠ on the chips above and in the today→proposed split. These are the structural gaps that don't belong to any single status:

⚠ No build / refresh trigger — requestRepositoryLstDetails has no caller in client code, so you can't rebuild or refresh an LST from the UI; the trigger is server-side and the UI is just a viewer.
⚠ No build diagnostics — the per-repo clone → parse → build → publish logs live only in CI / on disk, so the UI can't say why a repo failed to ingest. (Connector “ingested” / lastIngestedAt is a different concept — artifact-source ingestion, not LST.)
⚠ Staleness is unreliable — we don't actually know how far behind the repo an LST is. Repository.changeset is the SCM HEAD as Moderne last observed it (which may itself be stale), and there's no continuous polling of the SCM. So ‘N commits behind’ would frequently lie: the repo may have had no new commits since the LST was built, or many — we can't tell from inside the platform. The proposed model drops the ‘Stale’ state for this reason; surfacing a number we can't trust is worse than not surfacing it.
⚠ Pending vs Queued used to look the same — both were grey ‘waiting’ chips with different meanings (Pending = fetching LST; Queued = ready, waiting to run). The proposed model resolves this by collapsing Sync into Run: there's now one Queued state covering both kinds of waiting, so the ambiguity disappears.

Two open questions for the backend: (1) does Repository.changeset advance independently of LST builds (so the staleness comparison works), or is it copied from the latest LST (always equal)? (2) all five SCM providers share one client path for build / sync / run / staleness — differing only in URL + auth — so any per-provider freshness behaviour lives in the backend.

Proposed status colour model

A target where colour encodes the semantic class and the label names the exact status — applied consistently on every surface. Five classes, no gold: amber reads as caution, so it's reserved for “needs attention”; working is always blue. (The chips above still mirror today's UI; this is the recommendation.)

Waiting / neutral — grey
Pending · Queued · Canceled · Not started — nothing is wrong, nothing is done yet
Working — blue
Building · Partially ready · Running — in progress, no action needed
Ready / done — green
Available · Synced · Ready · Finished · Published
Needs attention — amber
Skipped · No LST — not a crash, but you probably need to act (re-ingest, check config)
Failure — red
Failed · Error — something broke

Colour answers “what kind of state?”; the label answers “which one.” This also fixes the audit findings: Canceled becomes grey everywhere (no more grey-vs-gold), and Building stops looking like a warning. Same-colour pairs that are genuinely the same class (Pending / Queued) stay distinguished by their label and column.

Indeterminate progress, not percentages. Running shows an animated blue bar with no percentage. We don't have a reliable signal for what ‘complete’ means per repo / LST — the engine doesn't emit normalised progress and repos vary wildly in size, so a number would frequently lie. The bar's motion communicates ‘working, no action needed’ without claiming how far along we are. Once the repo reaches a terminal state, the discrete outcome (Finished · Error · Canceled · No LST) replaces the bar. An org-level run header can still show an aggregate count (e.g. “26 of 38 finished”) separately.
Sync collapses into Run. The platform stops exposing Sync as its own column. Repos with a usable LST start in Queued — which now covers both ‘LST is being fetched & decrypted’ (old Pending) and ‘LST is ready, waiting for a run slot’ (old Queued) — then move to Running. Repos that are already synced enter Running immediately. Sync's terminal states fold into the run's: sync Failed → Error, sync Skipped → No LST, sync Canceled → Canceled. One status column, one set of states; the user doesn't have to mentally track two parallel lifecycles.

The whole CLI lane runs in CI / on disk — its per-repo clone → parse → build → publish logs are not surfaced in the platform, which only sees the published artifact.
